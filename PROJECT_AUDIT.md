# NetMind AI - Project Audit

## A. Architecture
The NetMind AI platform is designed as an end-to-end intelligent network observability and incident management system.
- **Frontend:** Next.js (React) application serving as the presentation layer.
- **Backend:** FastAPI (Python) exposing RESTful APIs.
- **Databases:** PostgreSQL (core relational data: users, incidents, telemetry records), Redis (caching, sessions, fast lookups).
- **Event Streaming:** Kafka for high-throughput ingestion of telemetry and anomalous events.
- **MLOps:** MLflow for storing, tracking, and dynamically serving baseline ML models (Isolation Forest, HistGradientBoosting).
- **AI/Agents:** LangGraph integration for agentic root-cause analysis (fetching logs, runbooks, recommending mitigations).
- **Vector Search:** Qdrant (planned/in-progress for RAG capabilities over runbooks).

## B. Current working functionality
- **Auth & RBAC:** JWT authentication is implemented. Users can log in, and RBAC is enforced on specific backend routes (e.g., mitigating incidents).
- **Live Incidents:** The Dashboard and Incidents pages actively fetch live incidents from `/api/v1/incidents`.
- **E2E Data Pipeline:** The backend successfully handles simulated failures, processes them through Kafka, triggers ML anomaly detection, and creates actionable incidents in PostgreSQL.
- **Agentic Workflow:** The `incident_worker` successfully orchestrates LangGraph to investigate detected anomalies and advance their state.
- **Model Training:** `train_baselines.py` trains models locally on synthetic telemetry data and logs the artifacts and evaluation metrics directly to MLflow.

## C. Broken functionality
- **Form Submissions:** The "Save Configuration" button in `Settings` does not intercept the submit event, causing a full page reload and losing state.
- **File Uploads:** The "Upload Document" button in the Knowledge Base does absolutely nothing.
- **Table Actions:** The "Details ->" button on the Devices page is a dead link.
- **Navigation:** There is no way to click an incident on the Incidents page and navigate to the Investigation page (the Investigation page is disconnected).

## D. Hardcoded/fake data
- **Devices Page:** The entire list of devices (core-rtr-01, etc.) is hardcoded in the frontend array.
- **Audit Logs:** The entire table of logs in the `audit` route is a static JSON array.
- **System Health:** OpenTelemetry metrics (1.2M requests, 0.01% error rate, 99.99% uptime) are static strings.
- **Knowledge Base:** The "142 documents currently indexed" claim and the document table are hardcoded.
- **Dashboard Metrics:** "Devices Monitored: 4" is hardcoded. "Pending Approvals" badge says "Phase 6".

## E. Placeholder UI
- **Investigation Chart:** A gray div explicitly labeled "Metric chart visualization placeholder" sits in the Investigation page.
- **TopologyViewer Fallback:** If the API fails, a text message says "No topology data found. Run the simulator to seed the environment."

## F. Backend/frontend mismatches
- **Port Mismatch:** The backend runs on port `8001` (per `docker-compose.yml`), but `TopologyViewer.tsx` statically attempts to fetch from `http://localhost:8000/api/v1/network/topology`.
- **Incident Statuses:** The frontend expects incident status to be `CONFIRMED` to show up as a pending approval, but the backend agent workflow often uses internal states like `WAITING_FOR_APPROVAL`.
- **Unused APIs:** The backend has a fully functional `/api/v1/predictions` endpoint, but the frontend Predictions page is entirely hardcoded and makes no HTTP requests.

## G. ML credibility problems
- **Fake Metrics:** The frontend Predictions page boasts a "92.4% Prediction Accuracy" and lists "High Risk Devices: 4". These are purely hardcoded strings. An interviewer will instantly spot this if they look at the network tab.
- **Fake Features:** The Upcoming Risk Forecast warns of "Predicted memory exhaustion". The backend synthetic dataset *only* generates CPU and Latency metrics. There is no memory data in the system.
- **Model Health:** The KS Tests and Latency Variances shown on the Model Health page are completely fabricated.

## H. Security issues
- **JWT Storage:** The frontend stores the JWT token in `localStorage` (`netmind_token`), which is vulnerable to Cross-Site Scripting (XSS) attacks. HttpOnly cookies should be used.
- **Hardcoded Secrets:** Database passwords and JWT secrets are likely exposed in `.env.example` or default fallback values in the backend code.
- **CORS Configuration:** The backend CORS origins might be overly permissive for local development.

## I. UX problems
- **Missing Loading States:** Most of the hardcoded pages instantly snap into view without skeleton loaders, making them feel fake.
- **Dead Ends:** The Investigation page hardcodes `incidentId = "INC-26185a09"`. A user cannot actually investigate real incidents generated by the pipeline.
- **Terminology:** The system uses "Anomalies", "Incidents", and "Alerts" interchangeably in the UI, causing cognitive load.

## J. Interview-risk areas
An interviewer will likely ask:
- *"Where does this 92.4% accuracy come from?"* -> You will be forced to admit the UI is hardcoded, despite having a real MLflow backend.
- *"How is this 'memory exhaustion' prediction generated?"* -> You will have to admit the feature doesn't exist in the data.
- *"What happens when I click Upload Document?"* -> Nothing happens.
- *"Why is the topology graph broken?"* -> Due to a port mismatch (8000 vs 8001).
- *"Where are these 142 documents stored?"* -> Qdrant integration is incomplete/hardcoded on the frontend.

## K. Recommended implementation order

### Prioritized List:

**P0 (Broken/Core Functionality - Fix Immediately)**
1. Fix the port mismatch in `TopologyViewer.tsx` (`8000` -> `8001`) so the graph actually renders.
2. Wire up the `/api/v1/predictions` endpoint to the frontend Predictions page to remove the fake 92.4% accuracy and replace it with real MLflow data.
3. Dynamically route the Investigation page to accept an `id` parameter so users can click an incident and see real details.

**P1 (Credibility and Interview-Critical - Fix Before Demos)**
4. Remove the "memory exhaustion" hardcoded warning. Ensure all frontend ML claims align exactly with the CPU/Latency synthetic dataset.
5. Replace the hardcoded `app/devices/page.tsx` table with a real fetch to `/api/v1/network/devices`.
6. Replace the hardcoded OpenTelemetry metrics on the System Health page (or clearly label them as mock/planned).

**P2 (UX/UI - Enhance Polish)**
7. Add proper loading skeletons to all pages instead of raw text.
8. Fix the Settings page "Save Configuration" form submission reload bug.
9. Ensure consistent terminology (standardize on "Incidents" for actionable items).

**P3 (Optional Enhancements - Later Phases)**
10. Implement the actual file upload logic for the Knowledge Base.
11. Migrate JWT storage from `localStorage` to HttpOnly cookies for enterprise security.
12. Build out the real `app/audit/page.tsx` backend integration.
